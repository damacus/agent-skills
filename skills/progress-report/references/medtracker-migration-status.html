Migration readiness · 6 October 2026

The Loco replacement is progressing, but cutover is not ready

Working medication and sign-in features are already published. The latest care delivery is published after clean review and all 160 browser cases passed. Several required application areas and the full release rehearsal remain unfinished. First production requires core care/account/public API workflows, automated NHS dm+d import/reconciliation and scanner, medication reviews/background refresh, complete administration, time-limited support, household export/closure/retention holds/deletion, avatars, complete devices/sessions and automatic live dose/stock updates. Offline capture, portable imports, acceptance of both native apps, FHIR/SMART/MCP and optional AI/provider lookup are deferred from that gate, but remain in the full migration goal. PDFs must match. Both scratch architectures and saved-state rollback remain required.

Keep production on the existing application.

The root Loco app is a working replacement in development, but it does not yet cover every capability needed for a safe wholesale switch.

Completion means all eight approved migration areas: preserved data and permissions, full account/care/API/client/browser behaviour, durable workers, both scratch-image architectures and a populated rollback rehearsal. Acceptance, merging and deployment are separate states. No merge or live deployment is authorised.

01 · Application capability

Application foundation and existing data

Partly complete

What works

Loco owns the root application, routes and everyday Task commands. Rails is independently runnable as the rollback application. Guarded schema adoption and tenant access are implemented. Foundation acceptance is recorded; the corrected persistence suite now passes 21 tests, including unchanged populated records and serialised concurrent adoption.

What remains

The complete persistence and release areas still need a populated saved-state restore rehearsal. The owner has approved rollback to an independent pre-cutover database snapshot, accepting loss of all new Loco data. Passing synthetic adoption tests does not establish that production can be switched safely.

What closes this area

Preserve a pre-cutover dump or stop a replica following before Loco writes. Prove that this independent saved state restores and Rails operates on it. Preserve existing records during Loco adoption; compatibility with Loco-created data and lossless post-cutover rollback are not required.

02 · Application capability

Sign-in and account security

Partly complete

What works

Password sign-in, persistent sessions, OAuth, MFA, recovery, supported passkeys, signup, invitations and verification/resend are published. The owner permits clearing historical passwords and MFA enrolments and invalidating old sessions, with secure re-enrolment before clinical access. Authentication must run inside MedTracker using its own daisyUI pages and database. Better Auth RS is selected, with OrganizationPlugin for households and multiple memberships. Implement it through normal account and household journeys; no dependency is installed yet.

What remains

Implement the selected embedded library and verify the Rodauth features actually used, including transaction/audit integration, signup access rules, tenant membership authority, credential revocation and account closure. Password reset, email change and remaining settings still need complete implementation and security evidence. Rauthy and all separate identity services are rejected. The selected dependency has not been installed.

What closes this area

Complete every account and security journey through the real browser and client interfaces, including failed and concurrent requests, existing credentials, withdrawal, recovery and supported replacement. Finish security review and exact published-commit checks.

08 · Application capability

Scratch images, cutover and rollback

Not yet proved

What works

The old application and useful source/PR inputs remain available for rollback and migration. No production switch, merge or deployment has occurred. Unsupported historical passkeys may be invalidated; counting affected accounts is not a cutover gate. Authentication and MFA requirements remain.

What remains

Final server and worker scratch images must pass on both amd64 and arm64. Missing assets, complete application journeys, saved-state cutover/rollback and obsolete Task/helper removal remain release gates. Restore uses the independent pre-cutover state and may discard all new Loco data, as explicitly approved.

What closes this area

Build and run both scratch architectures for server and worker. Prove saved-state restoration and Rails operation, plus exclusive application write ownership: stop Rails servers, workers and schedulers before Loco starts, and stop Loco before restoring Rails. Complete broad independent review. Live production actions still need separate approval.

What gets us from here to the end goal

These groups retain the complete goal. Coherent verified capabilities can be published while the remaining areas are implemented; none is a partial production cutover.

  2. Finish clients, browser and background workComplete the API/integration catalogue, native journeys, pages/locales/offline behaviour and every real job and schedule. Test complete behaviour rather than accepting an empty route or worker.
  3. Prove the whole replacement and rollbackRun final combined and interoperability checks, both scratch-image architectures, populated upgrade/rollback and broad review. Remove superseded tooling only after its replacement is proved. Publish verified work and check the exact commit in hosted CI.

The migration is accepted only when every area meets its full criteria. Merging and live deployment remain separate approval boundaries.
