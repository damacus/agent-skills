# Rails I18n and Locale Maintenance

Inspect the application's I18n configuration, default and available locales,
fallbacks, backend, locale directory structure, and translation-related gems.
Do not assume every YAML file is loaded or every project uses the default
Rails backend.

## Maintain the Contract

- Identify the canonical source locale and existing key hierarchy.
- Add, rename, or remove only keys required by the behavior change.
- Preserve interpolation names exactly across locales.
- Preserve pluralization categories required by each locale and backend.
- Keep HTML-safe keys and rendering conventions consistent with the project.
- Check lazy lookup, model/attribute translations, dates, numbers, and time
  zones at the layer where they are used.
- Validate YAML and run the repository's missing/unused translation checks.

When changing visible copy, trace the key from the view, component, mailer,
serializer, or validation to every supported locale. Do not duplicate English
into untranslated locales merely to make structural checks green unless that
is the repository's explicit fallback policy.

Use a dedicated translation capability when linguistic translation is needed;
this reference owns Ruby/Rails integration, key safety, and verification.
Domain-specific wording should be reviewed by someone who understands the
product language.
